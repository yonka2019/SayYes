# Design: Hebrew / Russian / English localization

Date: 2026-07-26
Status: approved

## Goal

SayYes currently ships Hebrew-only, RTL-only copy. Add Russian and English so the
creator can build invitations in any of the three, with a visible language
switcher and server-side auto-detection of the visitor's language.

## The two string classes

Every user-visible string in the app belongs to exactly one of these, and they
are handled differently:

1. **Chrome** — buttons, labels, validation messages, the escalating "לא" pleas,
   finale copy, page titles, dashboard text. App-authored. **Translated** into
   all three locales.
2. **Invitation content** — `recipientName`, `gateQuestion`, question texts,
   option labels. Typed by the creator in whatever language they chose.
   **Never translated.** Machine-translating a love note is both out of scope and
   a bad idea.

A third, in-between class: the **builder seeds** (`DEFAULT_GATE_QUESTION`, the
three default logistics questions and their options). These are app-authored but
become invitation content the moment the creator accepts them, so they are
translated and pre-filled in the creator's locale, then edited freely.

## Decisions

| Decision | Choice | Reason |
|---|---|---|
| Recipient's chrome language | The **invitation's** locale, not the visitor's browser | Hebrew content next to Russian buttons is a mixed-script, mixed-direction card. Content and chrome must agree. |
| URL scheme | Path prefix: `/he`, `/ru`, `/en` | Explicit and shareable. Standard App Router i18n layout. |
| Font | Rubik (`hebrew`, `latin`, `cyrillic` subsets) | Varela Round has no Cyrillic; Russian would fall back to a system font. One font keeps all three visually identical. |
| Library | Hand-rolled, `src/lib/i18n/` | 3 locales, ~110 strings. A dependency would bring its own routing and catalog conventions; hand-rolling keeps every rule a pure, unit-tested function, matching `dodge.ts` and `validation.ts`. |

## Auto-detection

Locale resolution is a **pure function** over three inputs, with this
precedence:

| # | Source | Rationale |
|---|--------|-----------|
| 1 | URL prefix (`/he`, `/ru`, `/en`) | Explicit wins. Bookmarks and shared links resolve deterministically, forever. |
| 2 | `sayyes_locale` cookie (1 year, `SameSite=Lax`) | The visitor's last manual switch. Beats a browser guess. |
| 3 | `Accept-Language` request header | The actual detection. Parsed with q-weights, highest first; matched on the base subtag so `ru-RU` → `ru`, `he-IL` → `he`, `en-GB` → `en`. Legacy `iw` maps to `he`. |
| 4 | `he` | Default. |

Resolution happens in `src/middleware.ts`, i.e. **server-side before render**, so
there is no flash of the wrong language and server components receive the correct
locale. A request without a locale prefix gets a `307` to
`/{resolved}{original-path}`. When resolution came from the header (no cookie
present), the redirect response also sets the cookie, so later navigation is
stable and the negotiation runs once.

The middleware matcher excludes `/api/*`, `/_next/*`, `icon.svg`, and any path
with a file extension — API routes must not be redirected, and static assets have
no locale.

## Components

### `src/lib/i18n/locales.ts` — locale primitives (pure, tested)

```ts
export const LOCALES = ["he", "ru", "en"] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale = "he";
export const DIR: Record<Locale, "rtl" | "ltr">;

export function isLocale(value: unknown): value is Locale;
export function localeFromPath(pathname: string): { locale: Locale | null; rest: string };
export function swapLocale(pathname: string, next: Locale): string;
export function negotiate(acceptLanguage: string | null): Locale | null;
export function resolveLocale(input: {
  pathname: string;
  cookie: string | null;
  acceptLanguage: string | null;
}): Locale;
```

Depends on nothing. `resolveLocale` implements the precedence table above and is
the single source of truth for detection — the middleware only wires it to the
request.

### `src/lib/i18n/dictionaries/{he,ru,en}.ts` + `src/lib/i18n/t.ts`

`he.ts` is the source of truth and exports a flat object of dotted keys
(`builder.name.label`, `invite.finale.title`, `plea.1`). `t.ts` derives
`type Dictionary = typeof he`; `ru.ts` and `en.ts` are declared `: Dictionary`,
so a missing, extra, or misspelled key is a **compile error**, not a runtime
fallback.

Interpolation is `{name}`-style placeholders resolved by a small `format()`.

```ts
export type Dictionary = typeof he;
export function getDictionary(locale: Locale): Dictionary;
export function t(dict: Dictionary, key: keyof Dictionary, params?: Record<string, string | number>): string;
```

Flat dotted keys rather than nested objects: greppable, and the key-set equality
test is trivial.

### Error codes replace error sentences

`validateDraft()` currently returns Hebrew sentences. It cannot, because the
locale is not known in `src/lib/`. Each `DraftErrors` field becomes:

```ts
type FieldError = { code: ErrorCode; params?: Record<string, string | number> };
```

`validateDraft()` stays the single source of truth for builder validity — the
form still uses it for live inline errors, and the create route still re-runs it
before writing. Only the payload changes: codes travel to the render site (and
into the `400` response body) and are translated there.

### `dodge.ts` pleas become keys

`PLEAS` (5 Hebrew strings) moves into the dictionaries. `dodge.ts` exports
`PLEA_KEYS` and `pleaKeyForCatches(catches): PleaKey | null`, keeping the
existing semantics exactly: nothing before the first catch, clamped at the last
so **it never gives up**. `scaleForCatches`, the flee/hop math, and `MIN_SCALE`
are untouched.

### `defaults.ts` becomes locale-aware

`DEFAULT_GATE_QUESTION` → `defaultGateQuestion(locale)`.
`defaultQuestions()` → `defaultQuestions(locale)`, returning the three logistics
questions with translated texts and option labels. Length limits and
`MIN_OPTIONS` / `MAX_OPTIONS` are unchanged.

### Routing

- Every page moves under `src/app/[locale]/`: `page.tsx`, `new/page.tsx`,
  `invite/[token]/page.tsx`.
- `src/app/[locale]/layout.tsx` becomes the root layout and owns
  `<html lang={locale} dir={DIR[locale]}>`. `src/app/layout.tsx` is deleted.
- `src/app/api/**` is unchanged — route handlers do not use layouts.
- `generateStaticParams` returns the three locales. Both dynamic pages keep
  `export const dynamic = "force-dynamic"`.
- `generateMetadata({ params })` supplies a per-locale title and description.
- Next 15: `params` is a Promise — `await` it, including the new `locale`.

### Invitation locale wins on the invite page

`Invitation` gains `locale String @default("he")` (existing rows are Hebrew, so
the default is correct). Applied with `npm run db:push`.

`/{urlLocale}/invite/{token}`: if `urlLocale !== invitation.locale`, the page
issues a `redirect()` to `/{invitation.locale}/invite/{token}`. A recipient who
opens a Hebrew invitation from an English browser still gets the Hebrew card,
RTL, with Hebrew buttons.

The share link the builder shows after creation is
`/{invitation.locale}/invite/{token}`.

No language switcher renders on the invite page — the content cannot follow it,
so offering the choice would only produce the mixed-language card this design
exists to avoid.

### `LanguageSwitcher`

Client component, three pills (`עברית` / `Русский` / `English`). On click: write
the `sayyes_locale` cookie, then `router.replace(swapLocale(pathname, next))`.
Rendered on the dashboard and the builder only.

### Visual system

- Rubik replaces Varela Round; the CSS variable is renamed `--font-varela` →
  `--font-app` in `src/app/globals.css`.
- Theme tokens, `CuteCard`, `Mascot`, `Sparkles`, and the heart SVG are unchanged.
- The LTR audit found no debt: the only physical-direction classes are the
  decorative blobs in `CuteCard` (`-left-10`, `-top-12 -right-8`), which are
  symmetric decoration, and `BuilderForm`'s `dir="ltr"` on the share-link input,
  which is correct in every locale.
- The dashboard shows a small `he` / `ru` / `en` badge per row so a
  mixed-language invitation list is readable at a glance.
- Phone width (390px) stays the primary viewport. The switcher pills sit in a
  `flex-wrap` row.

## Data flow

```
request  ──►  middleware: resolveLocale(path, cookie, Accept-Language)
              │  no prefix → 307 /{locale}{path}  (+ Set-Cookie if from header)
              ▼
         app/[locale]/layout.tsx  ──►  <html lang dir>  +  getDictionary(locale)
              │
              ├─ /{locale}          dashboard   chrome = URL locale
              ├─ /{locale}/new      builder     chrome = URL locale, seeds = URL locale
              │                                 POST /api/invitations { ..., locale }
              └─ /{locale}/invite/[token]
                     invitation.locale ≠ URL locale → redirect to invitation.locale
                     chrome = invitation.locale, content = as authored
```

## Error handling

- Unknown locale segment (`/de/new`) — not a valid `[locale]` value, so the page
  calls `notFound()` (`404`). The middleware only ever emits known locales.
- Malformed `Accept-Language` — `negotiate()` returns `null` and resolution falls
  through to `he`. Never throws.
- Unknown invite token — unchanged `404`.
- Already-answered token — unchanged `409`.
- Invalid draft — unchanged `400`, but the body now carries error **codes**; the
  client translates them.
- A locale value in the DB that is not a known locale (hand-edited row) — treated
  as `he` via `isLocale()`, rather than crashing the invite page.

## Testing

New unit tests (`tests/i18n.test.ts`):

- `negotiate()` — q-weight ordering, base-subtag matching (`ru-RU`, `he-IL`,
  `en-GB`), legacy `iw` → `he`, unknown languages → `null`, empty/garbage → `null`.
- `resolveLocale()` — full precedence table: path beats cookie beats header beats
  default; invalid cookie ignored.
- `localeFromPath()` / `swapLocale()` — round-trips, root path, nested paths,
  no-prefix input.
- Dictionary integrity — `he`, `ru`, `en` have identical key sets; no empty
  values; every `{placeholder}` in a Hebrew string appears in the Russian and
  English strings for that key.

Updated: `tests/validation.test.ts` asserts error codes instead of Hebrew
sentences; `tests/dodge.test.ts` asserts plea keys.

Manual click-through, per locale (`he` RTL, `ru` LTR, `en` LTR): dashboard →
switcher → builder incl. validation errors → link → gate (try to catch "no") →
questions → finale → reload link (read-only recap) → dashboard recap. Plus:
`/en/invite/{hebrew-token}` redirects to `/he/...`; a fresh incognito visit with
`Accept-Language: ru-RU` lands on `/ru`; `/de` is a `404`;
`document.body.scrollWidth <= window.innerWidth` at 390px in all three.

## Out of scope

- Machine-translating invitation content.
- Multiple languages per invitation.
- Retro-translating already-created invitations.
- Locale-aware date, number, or currency formatting — the app displays none.
- Any auth or deployment change.

## Consequences for project docs

CLAUDE.md's hard rule **"Hebrew only, RTL. All user-facing copy is Hebrew. Never
add English UI strings."** is superseded by this design and must be rewritten to
the new rule: all chrome flows through the dictionaries, no bare user-facing
string literals in components, `he` remains the default and the source-of-truth
dictionary. README gets a language section. The Russian and English copy is
written to match the Hebrew's flirty register and is worth a native proofread,
especially the five escalating pleas.
